## 3. 关键依赖版本约束（哪些不能升 / 哪些待升 / 哪些 beta）

| 依赖 | 当前版本 | 约束说明 | 风险级别 |
|---|---|---|---|
| `react` / `react-dom` | `19.2.3`（固定）| 与 React Compiler（`babel-plugin-react-compiler`）强绑定，升级前必须确认 Compiler 同步支持 | 高 |
| `babel-plugin-react-compiler` | `1.0.0`（固定）| 版本号为 `1.0.0` 且无 `^`，说明当前固定在此版本；React Compiler 仍处于快速演化期，升级需评估与 React 19 / Next.js 16 的兼容性 | 高 |
| `next` / `eslint-config-next` | `16.1.6`（固定）| 固定版本，跨主版本升级需评估 React Compiler 兼容性 + App Router 破坏性变更；`eslint-config-next` 必须与 `next` 同版本 | 高 |
| `@langchain/langgraph` | `^1.1.3` | 已从 0.x 演化到 1.x；API 趋于稳定，但仍需关注 minor 变更对节点 fan-out / state schema 的影响 | 中 |
| `@langchain/langgraph-checkpoint-postgres` | `^1.0.0` | 1.0.0 首个稳定版；PostgresSaver 内部连接池实现与 Supabase Supavisor 的兼容性需持续监控（CR-002）| 中 |
| `drizzle-orm` | `^0.45.1` | 0.x 系列；drizzle-orm 1.0 尚未发布（截至本文档创建）；升至 1.x 时 schema 定义 API 可能有破坏性改动，需专项评估 | 中 |
| `zod` | `^4.3.6` | v4 是最新稳定主版本；v3 → v4 有破坏性改动（parse API 略有调整）；项目已使用 v4，不应降回 v3 | 低 |
| `@supabase/supabase-js` | `^2.95.3` | 2.x 系列稳定；跨大版本升级需关注 realtime / auth 协议变化 | 低 |
| `ali-oss` | `^6.23.0` | 6.x 系列稳定；升级前关注 STS 接口变化 | 低 |
| `tailwindcss` | `^4` | v4 是新架构，与 v3 配置完全不兼容；已在 v4 上启动，不涉及升级；若引入第三方 Tailwind 插件需确认 v4 兼容性 | 低 |

- `babel-plugin-react-compiler 1.0.0` 无 `^`，属于精确锁定，非 beta 标记（React Compiler 已在 React 19 正式版中提供），但仍需关注与 Next.js 的集成稳定性。
- 无法仅从 `package.json` 判断各库是否处于 beta / RC 状态的，已在 §7 技术债中登记，待详细 D3 评估。

## 6. 开发工具链

### 6.1 pnpm Scripts

| 命令 | 作用 |
|---|---|
| `pnpm dev` | 启动 Next.js 开发服务器（`:3000`，热重载）|
| `pnpm build` | 生产构建（同时承担 TypeScript 类型校验，因无独立 tsc 脚本）|
| `pnpm start` | 启动生产服务（需先 `pnpm build`）|
| `pnpm lint` | 运行 ESLint（flat config，见 6.2）|
| `pnpm supabase:start` | 启动本地 Supabase 栈（Docker Desktop）|
| `pnpm supabase:stop` | 停止本地 Supabase 栈 |
| `pnpm supabase:reset` | 重置本地数据库（重跑所有 migrations）|

## 8. 升级流程约束

### 主版本升级（高风险）

主版本升级（如 Next.js 16 → 17 / React 19 → 20 / Drizzle 0.x → 1.x）须经过以下评估：

1. **React Compiler 兼容性**：React Compiler 与 React / Next.js 强绑定，主版本升级前确认 `babel-plugin-react-compiler` 是否同步更新
2. **LangGraph 兼容性**：LangGraph 节点拓扑、State schema、条件边路由函数签名在 breaking change 发布时需全面回归
3. **Drizzle 0.x → 1.x**：schema 定义 API 预期有破坏性改动，需专项 migration 评估 + 全表 schema 回归
4. **Supabase JS 主版本**：realtime / auth 协议可能变化；需回归核心流程（登录 → 发消息 → 读历史）

### Minor / Patch 升级

- 执行 `pnpm up` 更新到 caret 范围内最新版
- `pnpm-lock.yaml` 必须随代码一同提交（不提交 lockfile = CI 结果不可复现）

### Breaking Change 审查清单

每次升级后按顺序验证：

1. `pnpm build`（无 TypeScript 类型错误 + Next.js 构建成功）
2. `pnpm lint`（无 ESLint 报错）
3. 手测核心流程：拍题上传 → OCR → 引导一题完整四阶段（Understand → Plan → Execute → Review）
4. 检查 `PostgresSaver` 连接是否正常（发送消息后 checkpoint 落库）

**注**：实际升级 SOP 细节（含回滚步骤）见详细设计 D3 Runbook（待产出）；如有把握不大的细节，待详细 D3 完善后补充。

## 11. 文档维护责任与同步流程

### 维护责任

**muzi**（产品负责人 + 架构方向把控）负责评审每次 PR 时判断是否需要同步本文档。Claude 负责起草更新内容。

### 何时同步

以下任一变更发生后，须在**同一个 PR 内**同步本文档：

- `package.json` 中任意依赖版本发生 bump（包括 minor / patch）
- `supabase/config.toml` 版本相关配置变更（如 `major_version`）
- 高层架构 §8 任一决策（D1-D10）采纳方案发生变更
- 新增第三方服务（§5）或移除已有服务

### 同步流程

1. **bump 依赖**：执行 `pnpm up` 或手动修改 `package.json` 版本号
2. **验证构建**：跑 `pnpm build`（TypeScript 类型校验）+ `pnpm lint`
3. **更新本文档**：
   - §2 技术栈速览表：更新受影响行的精确版本列
   - §3 关键依赖版本约束：更新约束说明（如从 0.x 升至 1.x 时更新风险评估）
   - §10 版本快照：更新快照时间 + 关键主版本浓缩一句话
4. **检查反向锚点**：如关联决策也随版本升级而变更，对照高层 §8 确认 §9 反向索引仍正确
5. **提交 PR**：`package.json` 变更 + `pnpm-lock.yaml` 变更 + 本文档更新 **放同一个 PR**，确保版本快照与 lockfile 一一对应
