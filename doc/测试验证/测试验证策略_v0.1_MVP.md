## 3. 目录契约（elicit 单 app 适配）

**目标态**结构（不在当前阶段一次性铺出来）：

```
src/
  __tests__/                  # 单元测试，与就近模块同目录或集中存放（Phase 2 起）
    db/                       # Drizzle schema / mapper 契约测试
    agents/                   # 节点函数单测 (注入 fake model)
    lib/                      # withAuth / utils / stream parser
    types/                    # 枚举 / Zod schema 边界测试

  agents/
    demo/                     # Phase 2 起；fake model 跑 ChatGraph 端到端
      chatgraph-fake.ts       # tsx 入口

tests/                        # 根级，跨层 / 端到端 / evals（Phase 3 起）
  integration/                # 跨层链路：API + Graph + DB / RLS / data-custom chunk
  smoke/                      # 端到端：用户登录 → 上传题图 → OCR → 一轮对话 → 关闭
  evals/                      # L6 Agent 行为评测
    scenarios/                # 对话剧本 *.eval.ts
    judges/                   # LLM-as-judge prompt 模版
    golden/                   # muzi 人工标注的 baseline 分数集
    reports/                  # 历次回归报告 (gitignore，不入仓)

vitest.config.ts              # 统一 vitest 配置（Phase 2 起）
vitest.workspace.ts           # 多 project：unit / integration / smoke / evals 隔离（Phase 3 起）
```

约定：

- `src/__tests__/`：单元测试**与 `src/` 同包**，受 `tsconfig.json` 控制；**不得** `exclude` 测试文件，否则类型漏检。
- `tests/`：顶层目录、跨层 / E2E / evals 专用；新建前必须在 [CLAUDE.md](../../CLAUDE.md) 的"目录结构"章节登记。
- `demo/`：放在 `src/agents/demo/`，作用是 "fake model 跑通 Graph"，不入发布产物（Next.js 单 app，没有 `files` 字段，靠 `.dockerignore` 控制）。
- **Phase 0–1**（当前 → 详设完成）禁止创建 `tests/` 顶层目录；Phase 2 起允许，并同步更新 CLAUDE.md。

## 5. 各层执行要求（目标态）

### 5.1 L1 Type 验证（Phase 1+，PR 阻断）

- 根目录维护现有 `tsconfig.json`，**不**新增 `tsconfig.test.json` 等分裂配置（单 app 无必要）。
- `tsconfig.json` 中**禁止** `exclude` 任何 `__tests__/` 或 `*.test.ts`，让测试代码同样进类型检查。
- 新增 root script：`"typecheck": "tsc --noEmit"`，与 `pnpm lint` 并列。
- 任何 PR 必须先 `pnpm typecheck && pnpm lint` 全绿。

### 5.2 L2 Schema 校验（Phase 1+）

**边界 parse 原则**：`.parse()` 仅在以下边界使用：
1. **API 路由入口**：`/api/chat/[id]` 的 request body、`/api/oss/*` 等所有 `withAuth` 包裹的路由的入参
2. **客户端 ↔ 服务端 SSE chunk 边界**：`data-custom` chunk 的字段（`conversationId` / `title` 等）
3. **LangGraph state 边界**：`ElicitGraphStateSchema` 在 graph 入口 `.parse()` 一次，节点内部用 `z.infer` 派生的 TS 类型，**禁止热路径重复 parse**
4. **外部服务响应**：OSS STS 响应、Qwen-VL / DeepSeek 模型返回（如果是 structured output）

**禁止跨文件重复定义同义 Schema**：所有公开 Schema 集中在 `src/agents/schemas/` 与 `src/types/request/`，其他文件用 `z.infer` 导入类型。

### 5.3 L3 Unit Test（Phase 2+，PR 阻断）

**覆盖率基线**（沿用 rag-sdk ADR 0002 §5.3，对齐统一水位，不分阶段宽松）：

- **行覆盖率 ≥ 90%，分支覆盖率 ≥ 90%**
- 适用于 §6 列出的全部模块层（DB / Agent / API / 服务层），不分层豁免
- 未达标 = CI 阻断；个别确实无法测到的代码段使用 `/* v8 ignore next */` 显式标注，并在 PR 描述里说明原因
- Phase 2 启用时即按 90/90 验收（不设"入门宽松期"）

**核心目录**（必须覆盖）：
- `src/db/mappers/` — DB 映射逻辑（Mapper 是 contract 翻译器，bug 高发区）
- `src/lib/` — `withAuth` / `utils` / SSE stream parser
- `src/agents/schemas/` — Zod schema 自身的边界用例
- `src/types/enums/` — 枚举工厂 `createEnum` 行为
- `src/agents/nodes/` — 每个节点：注入 fake model，断言 state 转换 + Drizzle 写入

**UI 组件特殊处理**（`src/features/chat/chat-*.tsx`）：仍计入 90/90 覆盖率，但允许通过 RTL 组件测试 + `/* v8 ignore next */` 标注纯视觉分支（如 className 拼接）达成；视觉表现走 §6.2 手动验收，**不替代**覆盖率

**Mock 边界**：
- LLM client（`chatModel` / Qwen-VL）**必须可注入**；单测中**禁止**调真实 DeepSeek / Dashscope
- OSS STS / Supabase **必须**走 mock 或本地 Supabase 栈
- 真实 LLM / OSS 调用门控环境变量 `RUN_LIVE_TEST=1`，**不作 PR gating**（沿用 rag-sdk §5.5 精神）

### 5.4 L4 Agent Demo（Phase 2+，PR 阻断）

- 文件：`src/agents/demo/chatgraph-fake.ts`
- 入口脚本：`"demo:chat": "tsx src/agents/demo/chatgraph-fake.ts"`
- **无 key 可运行**：用 in-memory fake model（固定返回 Pólya 阶段 4 的成功流程），CI 无 DeepSeek key 也能跑通整条 graph 拓扑
- 真实 model demo 门控 `RUN_LIVE_DEMO=1`
- 作用：① CI 强制跑确保 graph 拓扑不烂；② Claude 自己开发时快速 smoke

### 5.5 L5 Integration & Smoke（Phase 3+）

**Integration**（`tests/integration/`）：覆盖跨层链路
- `chat-flow.test.ts`：`POST /api/chat/[id]` → `withAuth` → `compiledElicitGraph.stream` → PostgresSaver checkpoint → SSE chunk 协议
- `rls.test.ts`：Supabase RLS 行策略：用户 A 不能读用户 B 的 conversation
- `data-custom-chunk.test.ts`：`conversationNode` 写出 `data-custom` chunk → 客户端 `streamIterator` 正确解析
- `has-resolved-double-write.test.ts`：state 主写 + DB 镜像 + reconcile 兜底（C9）
- `migrations.test.ts`：每个 `supabase/migrations/*.sql` 应用后 Drizzle schema diff 必须为空（漂移检测）

**Smoke**（`tests/smoke/`）：端到端最小闭环
- `min-flow.test.ts`：用户登录 → 上传题图（mock OSS）→ OCR（fake model）→ 1 轮 chat → 关闭会话 → DB 状态正确
- 默认 fake model，CI 无 key 跑通
- Live 形态 `RUN_LIVE_SMOKE=1`，仅本地 / nightly 跑，**不**作 PR gating

### 5.6 L6 Agent Behavior Evals（Phase 3+，**不阻断 PR**）

> **设计原则**：沿用 rag-sdk ADR 0002 §9.3 边界精神——L6 给"分数 + 回归报告"，不是"通过 / 失败"，避免被 LLM 不稳定性误伤。

**剧本结构**（`tests/evals/scenarios/*.eval.ts`）：每个剧本定义
```ts
{
  name: "正常路径-Pólya四阶段-一次通关",
  input: [
    { role: "user", content: "我有道题不会..." },
    { role: "user", content: "[等待 agent 探路]" },
    ...
  ],
  expectedPhaseSignals: ["UNDERSTAND", "PLAN", "EXECUTE", "REVIEW"],
  expectedBehaviors: [
    "Agent 在 UNDERSTAND 阶段必须复述题意至少一次",
    "PLAN 阶段必须给出至少一条方法论提示，禁止直接给答案",
    ...
  ],  // 对应 PRD §8 行为契约
  judgeRubric: "/* 0-5 分判分细则 */"
}
```

**入门集**（Phase 3 落地，~10 个剧本）：
| 类别 | 数量 | 例 |
|---|---|---|
| 正常路径 | 3 | Pólya 四阶段一次通关 / 函数题 / 几何题 |
| 卡壳触发 | 2 | 学生 3 次同一阶段无进展 → StuckGuard 兜底 |
| 偏题触发 | 2 | 学生跑到其他题 → DeviationGuard 拉回 |
| 出范围 | 2 | 学生问高中题 → OutOfScopeGuard 拒答 |
| 多题处理 | 1 | 同时上传 2 题 → 选一弃一 |

**Judge 方案**（muzi 已选 LLM-as-judge）：
- Judge model：DeepSeek（与生产 `chatModel` 同模型，便于对齐）
- Judge prompt 模版集中在 `tests/evals/judges/`
- **校准集**：前 10 个剧本 muzi 人工评分作为 golden set，judge 跑回归与 golden 对齐，judge 自身与 golden 偏差 > 1 分要重写 prompt（防 judge 漂移）

**触发与报告**：
- 触发：① 详设 D2 落地后建立 baseline；② 之后任何 `src/agents/nodes/*` 或 prompt 文件改动的 PR 必须跑全套
- 命令：`pnpm evals`，输出到 `tests/evals/reports/<commit>-<timestamp>.json`
- **不阻断 PR**，但报告里任一剧本平均分回归 ≥ 0.5 分必须 muzi 显式确认才能 merge（PR description 留痕）

## 6. 各模块层最低验收

> elicit 是单 app 不是 monorepo，把 rag-sdk ADR §6 的"per-package 验收"重映射为"per-layer 验收"。

| 模块层 | 验收项 |
|---|---|
| **DB 层**（`src/db/`） | Schema ↔ migration 漂移检测（migrations.test.ts）；Mapper 单测；公共字段 helper 单测 |
| **Agent 层**（`src/agents/`） | 每个节点函数注入 fake model 单测；State Schema Zod 边界单测；fake-model demo 跑通；L6 evals baseline |
| **API 层**（`src/app/api/`） | `withAuth` 单测；每条路由 integration test；SSE chunk 协议契约测试 |
| **前端层**（`src/features/`, `src/stores/`） | Zustand store 状态机单测；`streamIterator` SSE 解析单测；关键组件 RTL 单测（list / message bubble）；视觉走 §6.2 手动验收 |
| **服务层**（`src/services/`） | OSS STS 签名单测（mock SDK）；预览 URL 签名单测 |

### 6.1 类型 / 契约层（横切）

- `src/agents/schemas/` 与 `src/types/request/` 的 Zod schema 必须有正反例单测（合法 input pass / 非法 input fail）
- `src/db/supabase/type.ts` 由 `pnpm supabase:type` 重生成，**禁止手改**；CI 中需检查 `type.ts` 是否与最新 schema 同步

### 6.2 视觉层验收（不在 vitest 内）

- 关键页面（聊天 / 历史会话列表 / 家长后台）由 muzi 在 PR 上线前手动 smoke
- Claude 落地前端改动后**必须截图**展示给 muzi（不能光说"组件已实现"）
- 可选未来引入 Playwright 视觉回归（不在 v0.1 范围）

## 7. Root Scripts（目标态）

> 当前 Phase 0–1 仅写入 `typecheck`；Phase 2 起逐步扩展。

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:cov": "vitest run --coverage",
    "test:watch": "vitest",
    "integration": "vitest run --project integration",
    "smoke": "vitest run --project smoke",
    "evals": "vitest run --project evals",
    "demo:chat": "tsx src/agents/demo/chatgraph-fake.ts",
    "check": "pnpm typecheck && pnpm lint && pnpm test:cov",
    "verify": "pnpm check && pnpm integration && pnpm smoke"
  }
}
```

- `pnpm check` = 单测层全绿（L1+L2+L3+lint）
- `pnpm verify` = 全工程验证（L1–L5），**Claude subagent 完成代码落地前必须跑这个**
- L6 `pnpm evals` **不**进 `verify`（不阻断）

## 9. 管理与边界

### 9.1 Hard Gate 配置（Phase 1 起，hook 强制）

**配置位置**：`.claude/settings.json`（项目级）+ `~/.claude/settings.json`（用户级兜底）

**Hook 强制项**：

| Hook 事件 | 触发条件 | 强制动作 |
|---|---|---|
| `PreToolUse(Edit/Write)` | 写入 `src/db/schema/*` | **必须**同 PR 改 `supabase/migrations/*` + 跑 `pnpm supabase:type`，否则阻断 |
| `PreToolUse(Bash)` | 命令是 `git commit` | 自动跑 `pnpm typecheck && pnpm lint`，失败阻断 |
| `Stop` | Claude 主线程 / subagent 结束 | 提示 "verify ran?"；若 working tree 有未跑 `pnpm verify` 的改动则警告 |
| `PreToolUse(Bash)` | 命令含 `--no-verify` / `--no-gpg-sign` | 直接拒绝（除非用户显式授权当次） |

**git pre-commit hook（本地兜底）**：使用 `husky` 或裸 `.git/hooks/pre-commit`，跑 `pnpm typecheck && pnpm lint`，失败阻断。

**CI Gating**（未来部署到 GitHub Actions / 阿里云 ECS pipeline 时）：

| 阶段 | 命令 | 是否阻断 |
|---|---|---|
| Lint | `pnpm lint` | ✅ |
| 类型 | `pnpm typecheck` | ✅ |
| 单测 + 覆盖率 | `pnpm test:cov` | ✅ |
| 集成 | `pnpm integration` | ✅ |
| Smoke（fake）| `pnpm smoke` | ✅ |
| Live smoke | `RUN_LIVE_SMOKE=1 pnpm smoke` | ❌ nightly |
| **Evals**（L6）| `pnpm evals` | ❌ 仅观察 + 报告 |

> 本地 hook **不替代** CI gating；CI gating 是终极防线，本地 hook 是"让 Claude 飞起来不撞墙"的缓冲。

### 9.2 禁止事项

- **禁止**缺失 L4 demo 或 L5 smoke（Phase 3 起）
- **禁止**仅依赖手动运行验证逻辑
- **禁止**单元测试调用真实 DeepSeek / Qwen-VL / OSS；live 链路一律走 `RUN_LIVE_*` gate
- **禁止**跨文件重复定义同义 Schema（§5.2）
- **禁止**把 L6 evals 分数作 PR gating（§9.3）
- **禁止**手改 `src/db/supabase/type.ts`（必须 `pnpm supabase:type` 重生成）
- **禁止**在前端 React 组件中导入带 `import 'server-only'` 的模块（违反时构建报错）
- **禁止** Claude subagent 使用 `--no-verify` 跳过 hook（除非 muzi 显式授权）

### 9.3 验证体系 vs 评测体系（沿用 rag-sdk ADR 0002 §9.3）

| 维度 | 验证体系（L1–L5） | 评测体系（L6 Evals） |
|---|---|---|
| 目的 | 代码正确性、契约一致性、可运行性 | 衡量 Agent 行为对齐 PRD §8 契约 |
| 产出 | 通过 / 失败（布尔） | 分数（0–5 加权平均）+ 回归对比 |
| PR 阻断 | ✅ | ❌（仅观察，回归 ≥ 0.5 需 muzi 确认）|
| 谁来管 | Claude 主力开发 + muzi 评审 | Claude 写剧本 + muzi 维护 golden set |
| 失败处理 | 必须修代码再 commit | 报告留痕，决定是否回滚 prompt |

**为什么 L6 不阻断**：① LLM 输出本身有随机性，硬阻断会因偶发抖动卡死 PR；② muzi 是唯一评审，硬阻断把判断权强制塞给 judge model 也不安全；③ 行为评测的价值是"早发现漂移"而非"门禁"，门禁应该交给 L1–L5。

### 9.4 用户级 CLAUDE.md 协同（"落地代码必须派 subagent"）

本文要求与 `~/.claude/CLAUDE.md` 的硬规则协同：

- 一切测试代码（写 `*.test.ts` / `*.eval.ts`）属于"落地代码"，**必须**派 Sonnet subagent 写
- subagent prompt 模版**必须**包含："完成后跑 `pnpm verify` 全绿才返回，否则继续修"
- 主线程职责：评审 subagent 产出的测试是否覆盖 §5 / §6 验收项，**不**亲自动手写测试
- 例外：本 ADR 自身 / 测试策略文档 / 模版（纯文档）—— 主线程可直接写

## 12. 风险与限制
