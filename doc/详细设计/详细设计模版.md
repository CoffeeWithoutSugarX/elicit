# 引思助手 详细设计模版

> **使用说明**
> - 每份详细设计对应一个版本，命名规则：`详细设计_v[版本号]_[功能名].md`（如 `详细设计_v0.1_MVP.md`）
> - 上游 = 同版本概要设计；下游 = 实施期源代码 + 测试代码
> - 详细设计回答「**Prompt 怎么写、算法怎么跑、错误怎么降级、Runbook 怎么操作、词汇库怎么准备**」
> - **不回答**：表 schema、API 字段名、State Zod 类型、模块函数签名、子系统拆分——那些已经在概要 / 架构定了

---

## 0. 本文档职责边界

> 详细设计是「**实施视角的可执行清单**」——把概要的接口契约、State Schema、节点签名，进一步落到 **Prompt 模板 / 关键词词典 / 算法伪代码 / 错误降级路径 / 部署 Runbook / 数据迁移脚本** 等可被人或 subagent 直接消费的层面。
> **不重新定义接口或表结构**，那是概要的事。

### 0.1 本文档写什么

- **Prompt 模板**：每个 LLM 调用节点的完整 system prompt + user prompt 占位结构 + few-shot 例子 + 输出契约（含 `phase_signal` 协议、JSON schema、字符长度约束）
- **节点算法**：守卫节点、路由节点等非 LLM 部分的判定逻辑（关键词命中规则、阈值、滑动窗口、fall-through 顺序）
- **词汇库与知识库**：知识点术语对照表、守卫关键词词典、数学思想清单 / 方法论 menu
- **实现资源清单**：所有要落到磁盘的非源码资源（prompts / csv / json / conf / yml）路径 + 来源 + 大小预估
- **错误处理与降级**：错误分类、备用模型方案、用户提示话术、重试 / 超时 / 限流策略
- **前端实现细节**：SSE chunk 演进兼容、卡片 reader 版本兼容、KaTeX 渲染容错、Zustand store 状态机
- **鉴权细节**：service_role client 隔离机制、启动日志埋点
- **可观测与性能**：日志埋点公约、Daily cost log、关键指标 / 告警阈值
- **部署与 Runbook**：服务器初始化、Supabase / Nginx 配置、首次部署步骤、备份恢复、数据迁移操作手册、备案流程
- **关键实现时序图**：跨子系统的关键路径 mermaid sequence diagram
- **测试用例设计**：跟测试验证策略 ADR 显式映射的剧本编号、单测用例集、smoke 验收步骤
- **关键设计决策**：每条含「问题陈述 / 候选方案 / 采纳 + 理由 / 备选退路」（沿用架构 §8 / 概要 §10 格式）
- **明确不做的设计议题** + **风险与未决问题** + **实施准入检查表（硬门控）**
- **修订记录 + 增量补丁**：版本演进留痕

### 0.2 本文档不写什么

| 不写 | 写在哪里 |
|---|---|

| API 路由的请求 / 响应字段 + SSE chunk schema 总线 | 概要设计 §5 / §9 |

## 2. 设计原则与命名公约

> 沿用上游 5 条原则（可读性 > 性能 / 就近迭代 > 完美重构 / 显式 > 隐式 / 拒绝早优化 / 文档化决策），新增详设专属公约。

### 2.1 沿用上游原则

简单列出 + 1 行说明（不重复展开架构 §2 / 概要 §2）。

### 2.2 Prompt 文件组织公约

- 目录：`src/agents/prompts/`，按节点类型再分子目录（`phases/` / `guards/` / `vision/`）
- 文件名：`{nodeName}.prompt.ts`（TS 文件，导出 `const`；不用纯 `.md`，便于类型化插值）
- 每个 prompt 文件**必须导出**：① `systemPrompt` 字符串（template literal）；② `userPromptTemplate(input): string` 函数；③ `outputContract` Zod schema；④ `fewShots: Array<{user, assistant}>`
- 模型参数（temperature / max_tokens / streaming / tool_choice）就近放在 prompt 文件，**不**全局集中
- 任何 prompt 改动必须更新 §19 修订记录 + 跑 L6 evals baseline 对比

### 2.3 节点算法目录公约

- 目录：`src/agents/nodes/{phases|guards|flow}/`（沿用 §7.3.1 目录骨架）
- 每个节点文件**必须导出**：① `{nodeName}Node` 函数；② `{nodeName}NodeName` 字符串常量；③ 同文件 `algorithm/` 子文件夹放纯函数（便于单测）
- 算法纯函数禁止有 I/O / DB / LLM 调用，只接受参数 + 返回值，便于 L3 单测注入

### 2.4 Runbook 编写公约

- 每条 Runbook 步骤必须标注：① **可幂等性**（重复执行是否安全）；② **回滚操作**（失败如何撤回）；③ **预期耗时**；④ **执行人**（开发 / 运维 / muzi 本人）
- 步骤编号一律 `[X.Y.Z]` 三级，便于演练打勾
- 涉及外部凭证（OSS RAM / Supabase service_role / ICP 备案）的步骤必须在末尾加"**敏感**"标注，提醒不入仓
- Shell 命令必须以 `$ ` 起首，输出片段必须有上下文说明（不只贴一坨日志）

### 2.5 词汇库 / 关键词词典编写公约

- 词典格式：JSON 或 CSV（依规模选）；JSON 用于 KV 映射，CSV 用于多列表格
- 必须有"来源"字段（教材出处 / muzi 经验 / 学术资料），便于评审
- 关键词词典**禁止**正则不闭包（如 `数学` 命中 `数学家`）—— 词典里写明命中边界（前缀匹配 / 全词匹配 / 包含匹配）
- 每个词典版本更新必须跑 L6 evals 全集做回归对比，回归 ≥ 0.5 分需 muzi 显式确认

## 4. Prompt 模板设计

### 4.1 Prompt 文件清单总览

| 文件路径 | 调用方 | 模型 | 流式 | 输出形态 |
|---|---|---|---|---|
| `src/agents/prompts/vision/visionNode.prompt.ts` | VisionNode | [model] | 否 | JSON |
| `src/agents/prompts/phases/{name}.prompt.ts` | {Phase}Node | [model] | 是 | 文本 + phase_signal |
| `src/agents/prompts/guards/{name}.prompt.ts` | {Guard}Node | [model 或 N/A] | — | — |

### 4.2 通用 Prompt 公约

#### 4.2.1 `phase_signal` 协议

```
phase_signal: "COMPLETED" | "STAY" | "ESCALATE"
```

- **COMPLETED**：本阶段完成，PhaseRouter 路由到下一阶段
- **STAY**：本阶段继续，等待用户下一轮输入
- **ESCALATE**：阶段卡壳超阈值或用户偏题/越界，路由到对应守卫

每个 Pólya 阶段 Prompt 必须在末尾要求模型输出该 signal。

#### 4.2.2 输出契约

- 默认输出格式：纯文本 + 末尾一行 `phase_signal: "..."`
- 结构化输出（如知识卡片）：JSON 包裹在 ` ```json ... ``` ` fence 内
- 字数约束：单条文本 ≤ NFR-QUALITY-001 阈值；知识卡片 JSON 不计

#### 4.2.3 few-shot 规模

- 每个 Prompt 配 **1~2** 组 few-shot（不超过，避免 token 浪费）
- few-shot 必须来自实际可能场景（PRD §8 行为契约的典型流）

#### 4.2.4 模型参数表

| 节点 | model | temperature | max_tokens | streaming | tool_choice |
|---|---|---|---|---|---|
| VisionNode | [model] | [val] | [val] | false | none |
| {Phase}Node | [model] | [val] | [val] | true | none |
